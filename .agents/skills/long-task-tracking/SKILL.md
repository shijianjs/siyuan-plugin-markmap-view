# Long Task Tracking

## 目标

通过 Git 仓库中的 Markdown 文档维护长期开发任务，使任务能够跨多个 AI 对话上下文持续推进。

核心要求：

- 任务状态必须持久化在项目文件中，不能依赖聊天记录。
- 每次开始新上下文时，必须能够根据项目文件恢复工作状态。
- 任务进度必须与实际代码、测试和验证结果一致。
- 任务清单必须完整、可核对，不能只记录笼统的进度描述。
- 不得擅自改变任务范围、验收标准或既定技术决策。

## 1. 适用条件

以下任一条件成立时，必须使用本工作流程：

- 预计需要跨多个 AI 对话上下文完成。
- 包含大量独立开发事项，需要持续盘点完成情况。
- 需要覆盖某个明确的功能集合、API 集合、官方示例集合或兼容性清单。
- 任务具有多个实施阶段，且中断后需要准确恢复。

普通的小型开发任务不需要建立额外的任务管理文档。

## 2. 文档组织

采用以下三级结构。

### 2.1 AGENTS.md：工作规范

只记录项目长期有效的开发约定，以及长期任务跟踪规则的触发要求。

不得在其中记录：

- 当前任务的具体进度。
- 临时待办事项。
- 当前对话的工作状态。
- 随任务变化的统计数据。

### 2.2 TODO.md：任务总览

固定放在项目根目录。

只记录：

1. 当前长期任务的名称和目标。
2. 每个任务的总体进度统计。
3. 当前尚未完成的主要事项。
4. 关键约束和注意事项。
5. 详细清单、技术文档的相对路径。

TODO.md 必须保持简短，原则上不直接容纳大型明细清单、实现细节和开发历史。

建议结构：

```markdown
# TODO

## 任务名称

任务目标的简短描述。

- 总计：120
- 已完成：75
- 明确不做：10
- 待完成：35

详细清单：[coverage.md](docs/development/coverage.md)

### 当前待办

- [ ] 完成剩余 3D 示例
- [ ] 完成剩余图表类型示例
- [ ] 完成剩余交互类示例
- [ ] 执行全量验证

### 注意事项

- 覆盖全部官方示例类型，不局限于 3D。
- 排除项必须记录具体理由。
- 已完成事项的实现细节保留在对应源码中。
```

多个长期任务可以在同一个 TODO.md 中分别建立章节。

### 2.3 专项文档：详细任务状态

按照任务类型建立专项文档，放在 `docs/` 或其他合适的项目目录。

例如：

```text
project/
├── AGENTS.md
├── TODO.md
├── docs/
│   └── development/
│       ├── demo-coverage.md
│       ├── demo-conventions.md
│       └── technical-decisions.md
└── demo/
```

专项文档负责保存：

- 完整任务清单。
- 每个事项的状态。
- 明确排除的事项及理由。
- 任务范围和统计口径。
- 必要的技术决策和限制。
- 尚未解决的问题及验证结果。

不要为了形式而创建多个文档。一个专项文档能够完整管理任务时，就不要拆分。

## 3. 任务清单规范

### 3.1 建立完整任务集合

当任务涉及明确的对象集合时，必须先建立完整清单，再开始批量实施。

例如：

- 官方 Demo 示例。
- API 接口。
- UI 组件。
- 数据格式。
- 浏览器兼容性。
- 平台适配。
- 功能测试用例。

清单必须覆盖任务约定范围内的全部对象，不能只列出容易完成的部分。

对于来自外部项目的清单，必须记录：

- 来源名称及地址。
- 对应版本、Tag 或 Commit（如果适用）。
- 获取或核对日期。
- 纳入统计的范围。
- 不纳入统计的范围及理由。

不得将尚未调查完整的集合描述为完整清单。

### 3.2 每个事项必须归入明确状态

统一使用以下三种状态：

**待完成（Pending）**

- 尚未实现。
- 实现不完整。
- 尚未通过必要验证。
- 实际状态无法确认。

必须列出具体名称。

**已完成（Done）**

- 已实现。
- 已通过该事项要求的验证。
- 能够在仓库中找到对应实现或验证依据。

只在统计中计数，默认不需要重复列出所有名称。

**明确不做（Excluded）**

- 明确决定不纳入当前任务范围。
- 必须记录具体名称及排除理由。
- 不得将尚未实现或暂时无法实现的事项直接归为排除项。

不得引入其他状态替代这三种基本状态。

如果存在阻塞问题，应在待完成事项旁记录阻塞原因，而不是因此改变其状态。

### 3.3 统计规则

所有统计必须满足：

```text
总数 = 已完成数 + 明确不做数 + 待完成数
```

每个事项只能属于一个状态。

禁止：

- 重复计数。
- 遗漏事项。
- 将未验证的实现计为完成。
- 将没有明确理由的事项计为排除。
- 通过修改总数掩盖未完成事项。
- 未经确认擅自缩小统计范围。

如果无法确认总数，应明确标注统计尚未完成，不得编造数字。

### 3.4 清单示例

```markdown
# Demo Coverage

## 来源与范围

- 来源：https://example.com
- 版本：v1.0
- 核对日期：2026-11-02
- 范围：全部官方示例

## 统计

| 状态 | 数量 |
|---|---:|
| 总计 | 120 |
| 已完成 | 75 |
| 明确不做 | 10 |
| 待完成 | 35 |

## 明确不做

| 名称 | 排除理由 |
|---|---|
| Example A | 依赖不支持的商业服务 |
| Example B | 使用项目不支持的 API |

## 待完成

### 3D
- [ ] Example C
- [ ] Example D

### Chart
- [ ] Example E
- [ ] Example F

### Other
- [ ] Example G
```

注意：

- 待完成事项必须能够定位到具体对象。
- 已完成事项只统计数量，不必重复维护名称列表。
- 排除事项必须保留名称和理由。
- 分类必须覆盖完整任务范围，不能只维护部分分类。

## 4. 开始任务或恢复任务

每次开始工作，必须按以下顺序执行：

1. 读取项目 `AGENTS.md`。
2. 读取项目根目录 `TODO.md`。
3. 读取 TODO.md 中引用的相关专项文档。
4. 检查 `git status` 和相关 Git diff。
5. 检查当前待办事项对应的实际源码。
6. 核对文档状态与代码实际状态是否一致。
7. 确认本次准备处理的具体事项。

发现文档与代码不一致时：

- 以实际代码和验证结果为依据重新核对。
- 不得仅凭旧对话中的完成声明标记事项。
- 修正错误的统计和状态。
- 无法确认时保留为待完成，并注明原因。

如果用户指定了具体任务或事项，优先处理该事项，不得擅自切换到其他任务。

## 5. 实施过程中的进度维护

每完成一个清单事项，立即维护对应专项文档。

状态转换规则：

```text
Pending ──实现并验证通过──> Done

Pending ──明确决定排除──> Excluded

Done ──发现实现或验证不合格──> Pending

Excluded ──重新纳入任务范围──> Pending
```

具体要求：

1. 状态变化必须同步更新统计数字。
2. 不得仅因代码已经写完就标记完成。
3. 发现新的任务对象时，先确认它是否属于既定范围。
4. 新增事项必须补充到清单并重新计算总数。
5. 删除、合并或调整任务范围必须有明确依据；必要时先征求用户确认。
6. 排除事项的理由必须具体，不能只写「不需要」「暂时不做」。
7. 重要技术决策必须保留，避免后续上下文重复讨论。

实现细节记录在对应源码或专项技术文档中，不要将其复制到任务清单。

## 6. 阶段性检查点

以下情况必须更新进度文档：

- 完成一批独立任务。
- 完成一个功能模块或任务分类。
- 发现影响后续实施的重要技术限制。
- 修改任务范围或排除事项。
- 发现原有统计或完成状态不准确。
- 准备暂停当前工作。

检查点必须包含：

- 本阶段完成的事项及数量。
- 尚未完成的事项。
- 验证结果。
- 新发现的问题和限制。
- 下一步具体处理哪个事项。

不要只记录「完成了部分工作」「继续剩余任务」等无法直接执行的信息。

不需要为每次小幅代码修改都创建一条独立进度日志。

## 7. 暂停和结束任务

用户要求暂停、结束当前工作或切换上下文时，必须先完成以下操作：

1. 更新专项文档中的所有已确认状态。
2. 重新计算并核对所有统计数据。
3. 检查待完成清单是否遗漏事项。
4. 检查排除项是否具有明确理由。
5. 更新根目录 TODO.md 的总体进度和待办事项。
6. 记录当前阻塞问题和未解决的技术问题。
7. 写明下一次可以直接执行的具体工作。
8. 检查所有文档链接是否有效。
9. 检查 Git 工作区，确认文档与代码状态一致。

如果当前工作尚未完成，不得为了让进度看起来完整而改变任务状态。

不要自动提交 Git。是否提交以及如何提交遵循项目现有约定。

## 8. 新上下文的恢复要求

新对话必须能够仅通过项目文件恢复工作状态。

恢复时：

1. 读取 AGENTS.md。
2. 读取 TODO.md。
3. 读取相关专项文档。
4. 检查 Git 状态和相关代码。
5. 确认上次记录的下一步工作。
6. 核实该事项是否仍未完成。
7. 直接继续执行。

不得：

- 要求用户重复提供项目文档中已有的信息。
- 重复实现已经完成的事项。
- 擅自推翻已有技术决策。
- 将历史对话中的猜测当作项目事实。
- 因为新上下文不了解前因后果，就擅自删除或简化任务清单。

如果项目文档缺失必要信息，先检查源码、Git 历史和相关文档；仍然无法确定时，才向用户询问。

## 9. 执行原则

- 项目文件是长期任务状态的唯一持久化来源。
- 任务范围和验收标准必须明确。
- 任务清单必须具体、完整、可核对。
- 统计数据必须能够通过明细清单验证。
- 已完成、待完成和明确不做必须严格区分。
- 进度文档必须与代码实际状态一致。
- 不得为了追求文档简洁而丢失必要的任务信息。
- 不得为了追求文档完整而制造重复信息。
- 优先复用项目已有文档和目录结构。
- 不引入不必要的任务管理工具、数据库、脚本或工作流。
- 以最少的文档维护成本，保证长期任务能够准确、连续地推进。
